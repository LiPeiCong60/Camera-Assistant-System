# 技术栈详解

本文按端和能力整理项目使用的所有主要技术，说明在哪里使用、怎么使用、为什么使用。

## 1. 总体架构

```text
mobile_client 负责用户体验、相机、相册、overlay 和设备联动主控
device_runtime 负责树莓派云台、本地检测、跟踪和设备状态
backend 负责业务数据、媒体记录、AI Provider 和大模型调用
admin_web 负责后台管理
database 负责持久化结构
```

核心原则：

- 手机负责画面：最终照片/视频和主预览来自手机摄像头。
- 树莓派负责转动：设备端控制云台，不做生产 AI Key 管理。
- 服务器负责智能：AI Provider 统一由后端配置和调用。
- 后台负责管理：管理后台维护用户、套餐、模板、设备、媒体、AI 任务和 Provider。

## 2. mobile_client 技术栈

### Flutter / Dart

- 使用位置：`mobile_client/lib`。
- 怎么使用：构建 App 页面、状态、导航、表单、相机预览和设备联动 HUD。
- 为什么使用：跨 Android/iOS，适合快速实现相机工具、管理多个页面和复杂交互。

### `camera`

- 使用位置：拍摄页、设备联动页。
- 怎么使用：
  - `CameraPreview` 显示手机本地画面。
  - `takePicture` 拍照。
  - `startVideoRecording` / `stopVideoRecording` 录像。
  - `startImageStream` 抽帧推送给树莓派或做手机端识别。
- 为什么使用：必须直接控制手机摄像头；设备联动主画面也要求使用手机主摄。

### Google ML Kit Pose Detection

- 使用位置：模板上传、实时人物关键点、设备联动目标点。
- 怎么使用：
  - 模板上传后识别人像关键点。
  - 生成 `bbox`、`head_box`、`segments`、`shoulder_center`、`face_center`。
  - 实时画面识别人物框、骨架线和跟随点。
- 为什么使用：手机端直接获取人体关键点，避免树莓派承担主要视觉识别压力。

### 手机端 overlay 绘制

- 使用位置：`lib/features/overlay/camera_overlay_painter.dart`、`overlay_scene.dart`。
- 怎么使用：
  - 输入归一化坐标。
  - 根据相机预览尺寸、镜头方向、裁剪方式转换到屏幕坐标。
  - 绘制人体框、骨架线、模板框、模板线、中心点、AI 推荐框。
- 为什么使用：所有视觉叠加由手机绘制，保证主预览一致，避免服务器或树莓派返回像素坐标导致错位。

### WebSocket

- 使用位置：设备联动手机帧上行。
- 怎么使用：
  - 手机把 `camera` ImageStream 中的帧推送到 `/api/device/stream/mobile-ws`。
  - 树莓派端接收后做检测和跟踪。
- 为什么使用：局域网低延迟、实现简单，适合当前手机主控 + 树莓派控制的架构。

### `flutter_webrtc`

- 使用位置：`lib/services/device_webrtc_service.dart`。
- 怎么使用：保留 WebRTC offer/answer signaling 和视频 track 实验路径。
- 为什么使用：为未来更低延迟或标准实时音视频链路预留；当前默认主链路不是 WebRTC。

### `http`

- 使用位置：`MobileApiService`、`DeviceApiService`。
- 怎么使用：
  - 调用 `/api/mobile/*` 创建模板、历史、AI 任务。
  - 调用 `/api/device/*` 控制树莓派、读取状态、设置模式。
- 为什么使用：HTTP API 清晰稳定，适合业务和控制命令。

### `shared_preferences`

- 使用位置：设置页、详细设置、服务地址。
- 怎么使用：保存后端地址、设备地址、拍摄默认项、overlay 开关、扫描参数、手势设置。
- 为什么使用：轻量本地键值存储，适合 App 偏好设置。

### `image_picker`

- 使用位置：模板上传、相册选择。
- 怎么使用：选择本机图片生成模板或上传后端。
- 为什么使用：移动端读取相册的标准能力。

### `path_provider`

- 使用位置：AI 扫描候选帧、临时文件。
- 怎么使用：生成临时目录保存候选图片，上传后清理。
- 为什么使用：多角度扫描需要缓存临时帧，但不应该把所有候选图保存到相册。

### `image`

- 使用位置：部分图片编码和处理辅助。
- 怎么使用：处理本地字节、判断格式或转换。
- 为什么使用：补充 Flutter/平台相册 API 无法直接处理的图片操作。

### 相册保存

- 使用位置：`GallerySaveService`、Android `MainActivity.kt`、iOS `AppDelegate.swift`。
- 怎么使用：
  - Android 通过平台通道写入 MediaStore。
  - iOS 通过平台通道请求相册写入权限并保存。
- 为什么使用：`camera` 产物默认是 App 临时文件，用户需要最终照片/视频进入系统相册。

### Android Kotlin 原生层

- 使用位置：`mobile_client/android/app/src/main/kotlin/.../MainActivity.kt`。
- 怎么使用：通过 Flutter MethodChannel 接收 Dart 调用，写入图片和视频到 Android MediaStore。
- 为什么使用：系统相册写入属于平台能力，Dart 层不能完全覆盖 Android 不同版本的媒体库行为。

### iOS Swift 原生层

- 使用位置：`mobile_client/ios/Runner/AppDelegate.swift`。
- 怎么使用：通过 Flutter MethodChannel 请求相册写入权限并保存图片/视频。
- 为什么使用：iOS 相册权限和保存入口必须走系统 Photo Library API。

## 3. device_runtime 技术栈

### FastAPI / Uvicorn

- 使用位置：`device_runtime/api/app.py` 和 `api/routes`。
- 怎么使用：提供设备健康检查、会话、控制、状态、推流、模板、抓拍、AI 兼容接口。
- 为什么使用：轻量、易部署到树莓派，手机端可以直接通过 HTTP/WebSocket 控制。

### WebSocket

- 使用位置：`/api/device/stream/mobile-ws`、`/api/device/preview-ws`。
- 怎么使用：
  - `mobile-ws` 接收手机推送帧。
  - `preview-ws` 作为调试预览保留。
- 为什么使用：手机和树莓派在局域网内实时通信，比轮询上传单帧更适合连续帧。

### OpenCV

- 使用位置：帧解码、图像缩放、overlay 调试绘制、JPEG 编码。
- 怎么使用：把手机帧转为 BGR 图像，送入检测器和跟踪流程。
- 为什么使用：Python 端图像处理基础库，兼容 MediaPipe 和调试输出。

### MediaPipe

- 使用位置：`vision/detector.py`。
- 怎么使用：
  - 姿态关键点用于人体框和跟踪。
  - 手部关键点用于手势抓拍。
  - 人脸点用于人脸跟随和调试 overlay。
- 为什么使用：树莓派可运行、部署成本低；在需要时打开，不需要时关闭以降低负载。

### pyserial

- 使用位置：`control/gimbal_controller.py`。
- 怎么使用：通过串口发送 TTL 总线舵机控制帧。
- 为什么使用：真实云台硬件使用 TTL 总线舵机，串口控制直接可靠。

### TTL 总线舵机控制

- 使用位置：`TTLBusSerialDriver`、`GimbalController`。
- 怎么使用：
  - 角度映射为脉宽。
  - pan/tilt 两轴分别控制。
  - 支持回中、相对移动、连续控制、跟踪缓动。
- 为什么使用：比普通 PWM 舵机更适合总线化、可配置 ID 的云台结构。

### 跟踪控制算法

- 使用位置：`control/tracking_controller.py`。
- 怎么使用：
  - 输入目标点和画面中心/模板目标点偏移。
  - 使用死区、增益、最大步进、刹车区、反向保护、灵敏度。
  - 输出 pan/tilt 修正量。
- 为什么使用：直接按偏移转动容易抖动或过冲，需要平滑和限幅。

### aiortc

- 使用位置：`api/routes/webrtc.py`。
- 怎么使用：保留 WebRTC offer/answer 实验接口。
- 为什么使用：为未来实时传输切换预留；当前主链路可在缺少 `aiortc` 时继续使用 WebSocket。

## 4. backend 技术栈

### FastAPI

- 使用位置：`backend/app/main.py`、`app/api/routes`。
- 怎么使用：定义 `/api/mobile/*`、`/api/admin/*`、`/api/health`。
- 为什么使用：Python 生态成熟、类型友好、易于和 Pydantic/SQLAlchemy 集成。

### SQLAlchemy 2

- 使用位置：`app/models`、`app/repositories`、`app/services`。
- 怎么使用：ORM 映射核心表，仓储层封装查询，服务层提交事务。
- 为什么使用：比手写 SQL 更容易维护复杂业务表关系。

### PostgreSQL / psycopg

- 使用位置：`DATABASE_URL`、`database/schema.sql`。
- 怎么使用：保存用户、套餐、模板、媒体、AI 任务和 Provider 配置。
- 为什么使用：关系型数据清晰，支持 JSON 字段、约束、索引和事务。

### Pydantic

- 使用位置：`app/schemas`。
- 怎么使用：校验请求和响应，归一化 `capture_type`、`task_type`、`target_box_norm`。
- 为什么使用：保证移动端、后台和数据库之间的字段一致。

### httpx

- 使用位置：`app/services/ai_provider_service.py`。
- 怎么使用：调用 OpenAI-compatible 视觉模型接口，处理超时、错误和响应解析。
- 为什么使用：后端统一调用外部 AI Provider，不把 Key 下发给手机或树莓派。

### python-multipart

- 使用位置：文件上传接口。
- 怎么使用：接收照片、视频、模板图片、多角度候选图。
- 为什么使用：移动端上传媒体文件的标准方式。

### 后端 AI Provider 抽象

- 使用位置：`ai_provider_configs`、`AiProviderService`。
- 怎么使用：
  - 管理后台维护 Provider。
  - 套餐 `feature_flags` 选择默认或可用 Provider。
  - 后端生成结构化视觉提示词。
  - Provider 返回 JSON，后端写入 `ai_tasks`。
- 为什么使用：统一 AI 配置，避免多端分散保存 Key 和模型参数。

## 6. database 技术栈

### PostgreSQL JSON 字段

- 使用位置：`templates.template_data`、`captures.metadata`、`ai_tasks.request_payload`、`response_payload`、`target_box_norm`、`ai_provider_configs.extra_config`。
- 怎么使用：保存模板关键点、媒体元信息、AI 请求/响应和 Provider 扩展配置。
- 为什么使用：视觉和 AI 数据结构会随功能演进，JSON 比固定列更灵活。

### 检查约束

- 使用位置：`capture_sessions.mode`、`captures.capture_type`、`ai_tasks.task_type/status`、`templates.status/type`。
- 怎么使用：数据库层防止非法枚举入库。
- 为什么使用：多端协作时不能只靠前端校验。

### 更新时间触发器

- 使用位置：核心表 `updated_at`。
- 怎么使用：更新记录时自动刷新时间。
- 为什么使用：后台列表和排查问题需要可靠更新时间。

## 7. AI 和视觉数据结构

### 归一化坐标

- 使用位置：模板、实时人物、AI 推荐框、跟踪目标。
- 怎么使用：所有跨端坐标都使用 `0..1`，手机端绘制前再转为屏幕坐标。
- 为什么使用：不同手机分辨率、横竖屏、预览裁剪都能复用同一数据。

### `template_data`

- 使用位置：后端模板、手机拍摄页、设备联动页。
- 怎么使用：保存人物框、头部框、关键点、骨架线、肩部中心点、面部中心点。
- 为什么使用：模板构图需要可重复加载和对齐的结构化数据。

### `target_box_norm`

- 使用位置：后端 AI 任务、背景锁定、手机 overlay。
- 怎么使用：AI 返回推荐人物位置框，手机端根据开关显示或隐藏。
- 为什么使用：背景锁定需要给用户看到“AI 推荐站位/构图范围”。

## 10. 为什么这样分工

### 为什么手机做主画面

手机摄像头质量高、用户直接取景、照片/视频最终也由手机保存。树莓派摄像头不适合作为用户最终预览来源，否则画质、延迟、方向、保存和相册都会变复杂。

### 为什么树莓派只负责转动

树莓派更适合连接舵机、执行控制命令和做必要的轻量检测。把主预览和最终媒体交给手机，可以减少树莓派负载，让云台响应更稳定。

### 为什么 AI 走后端

AI Key、Provider、模型和日志属于服务端配置。统一放后端可以：

- 避免 Key 泄露到 App 或树莓派。
- 支持后台切换 Provider。
- 记录 AI 任务和错误。
- 支持套餐级别能力控制。

### 为什么 overlay 在手机端绘制

手机知道真实预览尺寸、镜头方向、裁剪方式和 UI 布局。服务器或树莓派直接返回像素坐标会在不同设备上错位；归一化坐标 + 手机端绘制更可靠。

## 11. 安全和隐私

- 真实 API Key 只在后端 Provider 配置中保存。
- 手机端和树莓派端不应提交或保存生产 AI Key。
- 用户照片、视频、`uploads/`、`captures/`、`.env`、日志、模型权重不应提交到 Git。
- 多角度扫描候选帧是临时文件，只有最佳图按需求保存到手机相册。
- 设备联动最终照片/视频保存在手机相册，上传后端需要用户设置或明确动作。
