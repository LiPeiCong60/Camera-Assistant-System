# 云影随行项目说明

## 1. 项目定位

云影随行是一个面向自助拍摄、合影、短视频固定机位拍摄、校园活动记录和旅行打卡场景的多端智能拍摄辅助系统。它不是单纯的拍照 App，而是把手机、设备运行时、云台、后端、管理后台和多模态 AI 组合成一个“AI 虚拟摄影师”。

项目要解决的问题包括：

- 看不准：自拍或合影时，人离手机较远，难以判断主体是否居中、构图是否平衡。
- 调不稳：普通支架只能固定机位，人物移动后容易偏出画面。
- 站不好：用户不知道人应该站在哪里，背景、留白、人物比例是否合适。
- 选不出：连拍后需要人工筛选表情、清晰度、构图和背景最好的照片。

系统核心原则是：

```text
手机负责画面，设备负责转动，服务器负责智能，后台负责管理。
```

这句话对应到工程实现：

- 手机端使用本地摄像头作为主预览和最终照片/视频来源，保证画质、方向、相册保存和用户交互稳定。
- 设备端运行在树莓派或本机上，负责低延迟接收手机抽帧、视觉检测、目标跟随和 TTL 总线舵机云台控制。
- 后端统一保存业务数据、AI 任务、AI Provider 配置和调用结果，手机端和设备端不保存生产 AI Key。
- 管理后台负责运营管理、套餐、推荐模板、媒体记录、AI 任务排查和模型配置。

## 4. 模块与技术栈

### 4.1 手机端 `mobile_client`

技术栈：

- Flutter / Dart：跨平台 App、页面、状态和交互。
- `camera`：手机本地相机预览、拍照、录像和 `startImageStream` 抽帧。
- Google ML Kit Pose Detection：手机端人体关键点检测，用于模板构图和跟随点计算。
- `http`：调用业务后端和设备端 HTTP API。
- WebSocket：手机向设备端推送压缩后的摄像头帧。
- `flutter_webrtc`：保留低延迟 WebRTC 实验链路。
- `shared_preferences`：保存服务器地址、设备地址、设备联动草稿、扫描参数、拍摄设置。
- `path_provider` / `image_picker` / `image`：本地文件、模板图选择、图像处理。
- Android Kotlin / iOS Swift 平台通道：保存照片和视频到系统相册。

主要目录：

| 路径 | 职责 |
| --- | --- |
| `lib/app` | App 启动、服务地址加载、登录态引导。 |
| `lib/features/auth` | 登录、注册、认证控制器。 |
| `lib/features/home` | 首页、套餐详情、快速入口、模板管理入口。 |
| `lib/features/camera` | 普通拍照/录像、拍后上传、AI 分析入口。 |
| `lib/features/device_link` | 设备联动主页面，包含云台控制、手机推流、模板构图、AI 自动找角度、AI 背景锁定。 |
| `lib/features/device_link/parts` | 设备联动页拆分出的工具、状态、socket、widget、AI 结果格式化等局部模块。 |
| `lib/features/history` | 历史会话、历史照片、AI 选优、AI 分析结果展示。 |
| `lib/features/settings` | 详细设置、服务器地址、设备联动参数、AI 参数、overlay 参数。 |
| `lib/features/template` | 模板照片选择和模板创建。 |
| `lib/features/overlay` | 模板框、骨架线、AI 推荐框等 overlay 绘制。 |
| `lib/models` | 后端和设备端响应模型。 |
| `lib/services` | `MobileApiService`、`DeviceApiService`、`GallerySaveService`、WebRTC、缓存和本地图片解析。 |

手机端核心实现：

- 主画面始终使用手机本地 `CameraPreview`，设备端回传画面只作为兼容/调试链路。
- 设备联动时，手机通过 `startImageStream` 抽帧，按配置降低分辨率和帧率，再通过 WebSocket 推给设备端。
- 手机端保存拍照和录像结果到系统相册，再按设置决定是否上传后端创建媒体记录和 AI 任务。
- AI 自动找角度和背景锁定不是设备端自己决定，而是手机控制云台逐个扫描候选角度、缓存候选帧、统一上传后端，再根据后端 AI 返回的 `best_candidate_index` 控制设备回到最佳角度。
- `target_box_norm` 使用 0 到 1 的归一化坐标，手机端把它转换到预览画布上绘制 AI 推荐站位框。

### 4.2 设备运行时 `device_runtime`

技术栈：

- Python / FastAPI / Uvicorn：设备端 HTTP 和 WebSocket API。
- OpenCV：解码、缩放、处理手机帧。
- MediaPipe：人体、人脸、手部关键点检测。
- pyserial：通过串口控制 TTL 总线舵机。
- WebSocket：接收手机连续推送的图像帧。
- aiortc：保留 WebRTC 兼容实验接口。
- Pillow / numpy：图像处理和数组计算。

主要目录：

| 路径 | 职责 |
| --- | --- |
| `api/app.py` | FastAPI 应用入口，挂载设备端路由。 |
| `api/routes/status.py` | 健康检查、设备状态、运行配置、预览图和预览 WebSocket。 |
| `api/routes/session.py` | 打开/关闭设备会话，配置预览来源和控制模式。 |
| `api/routes/control.py` | 手动移动、模式切换、回中、跟随模式、灵敏度、目标点跟踪。 |
| `api/routes/stream.py` | 手机 WebSocket/NV21 推流和 HTTP 帧上传。 |
| `api/routes/templates.py` | 设备侧模板导入、上传、选择、清除。 |
| `api/routes/capture.py` | 设备侧抓拍触发、手机抓拍确认、文件列表和文件读取。 |
| `api/routes/ai.py` | 设备侧 AI 兼容接口、角度扫描、背景锁定、应用角度和应用锁定。 |
| `api/routes/webrtc.py` | WebRTC offer/answer 和兼容实验链路。 |
| `api/session_manager.py` | 设备会话核心状态，串联视频源、检测、控制、模板、AI 锁定和抓拍。 |
| `control/gimbal_controller.py` | mock/TTL 总线舵机驱动、角度限幅、平滑运动、反馈读取。 |
| `control/tracking_controller.py` | 根据目标点和画面中心/模板目标计算 pan/tilt 增量。 |
| `vision/detector.py` | MediaPipe/YOLO/HOG 检测、关键点、bbox、手势和异步检测。 |
| `vision/video_source.py` | 摄像头源、手机推流帧源和读取抽象。 |
| `services/frame_processor.py` | 单帧处理、可靠检测、overlay 数据生成。 |
| `services/control_service.py` | 控制模式和云台动作的业务封装。 |
| `services/template_service.py` | 模板导入、人物框识别、模板资料生成和修复。 |
| `services/ai_orchestrator.py` | 设备侧兼容 AI 扫描、背景锁定、锁机位拟合。 |
| `interfaces/ai_assistant.py` | 设备侧 SiliconFlow/OpenAI-compatible 调试 AI 封装。 |

设备端核心实现：

- `MobilePushFrameStore` 接收手机推来的帧，`MobilePushVideoSource` 将其作为设备检测输入。
- `VisionDetector` 使用 MediaPipe Tasks 或 fallback 方案识别人体、手部、人脸；可选 YOLO 作为人物 bbox 辅助，但默认依赖不安装 YOLO/torch。
- `FrameProcessor` 对检测结果做可靠性判断、稳定性计数、overlay 数据生成。
- `TrackingController` 将目标点偏移转换成控制命令，支持死区、增益、刹车区、步进限制和速度模式。
- `GimbalController` 将角度转换为舵机指令，支持 mock 驱动和 TTL 总线舵机驱动。
- 手势抓拍通过手部识别和倒计时触发；当前产品主链路可把抓拍委托给手机完成，保证照片来自手机相机。

### 4.3 业务后端 `backend`

技术栈：

- FastAPI：移动端和管理后台 HTTP API。
- SQLAlchemy 2：ORM 模型和仓储层。
- PostgreSQL / psycopg：业务数据持久化。
- Pydantic：请求响应模型、字段校验和归一化。
- httpx：调用 OpenAI-compatible 多模态视觉模型。
- python-multipart：接收照片、视频和多角度候选帧上传。
- OpenCV / Pillow / MediaPipe：图片压缩、模板图识别和视觉结构提取。

主要目录：

| 路径 | 职责 |
| --- | --- |
| `app/api/routes/mobile.py` | 手机端 API：登录注册、模板、会话、媒体上传、AI 分析、历史记录。 |
| `app/api/routes/admin.py` | 管理后台 API：用户、套餐、推荐模板、设备、媒体、AI 任务、Provider 配置。 |
| `app/services/mobile_service.py` | 手机业务服务，创建模板、会话、媒体记录、AI 任务和批量选优。 |
| `app/services/admin_service.py` | 后台业务服务，管理用户、套餐、订阅、模板、统计、AI Provider。 |
| `app/services/ai_provider_service.py` | 生产 AI Provider 调用、图片打包、Prompt 构造、JSON 解析和字段归一化。 |
| `app/services/template_pose_service.py` | 推荐模板图片上传后的姿态/人物框识别和模板数据生成。 |
| `app/models` | SQLAlchemy ORM 模型。 |
| `app/repositories` | 数据访问层，封装常用查询和持久化。 |
| `app/schemas` | Pydantic 请求响应模型。 |
| `app/core` | 配置、数据库连接、认证、错误和字段契约。 |

后端核心实现：

- 移动端上传媒体后，后端保存到 `uploads/captures/...`，生成可访问 URL，并写入 `captures`。
- AI 任务由 `MobileService` 创建，成功或失败都会写入 `ai_tasks`，避免前端因为 Provider 不可用而失去可追踪状态。
- `AiProviderService` 只实际实现 OpenAI-compatible 调用格式；数据库层可以保存 `anthropic_compatible`、`custom` 等配置，但调用适配器需要后续补齐。
- AI Provider 的 `base_url`、`api_key`、`model_name`、`temperature`、`max_tokens` 等通过后台配置，不写死在手机或设备端。
- 后端对模型返回做二次防御：抽取 JSON、归一化分数、限制云台角度、校验最佳候选/照片 ID、归一化推荐框。

- 对用户、状态、类型、会话、AI 任务等常查字段建立索引，便于后台筛选和排查。

## 5. 端到端功能流程

### 5.1 登录、套餐和模板

```text
手机端登录 / 注册
-> backend AuthService 校验或创建用户
-> 返回 access_token
-> 手机端读取套餐 / 订阅 / 模板
-> 用户可以上传模板照片
-> backend TemplatePoseService 识别人物框和姿态点
-> templates.template_data 保存归一化视觉结构
-> 手机端后续用于模板 overlay 和设备跟随目标计算
```

### 5.2 普通拍照和 AI 分析

```text
用户在手机端拍照
-> 手机保存到系统相册
-> 手机上传文件到 /api/mobile/captures/file
-> 后端保存文件并返回 file_url
-> 手机创建 capture 记录
-> 手机调用 /api/mobile/ai/analyze-photo
-> 后端读取 capture.file_url
-> AiProviderService 构造视觉模型请求
-> 模型返回 JSON
-> 后端写入 ai_tasks
-> 手机展示评分、摘要、推荐微调和推荐框
```

### 5.3 设备联动主链路

```text
用户打开设备联动页
-> 手机连接 backend 和 device_runtime
-> 手机打开本地 CameraPreview
-> 手机 startImageStream 抽帧
-> WebSocket 推送到 /api/device/stream/mobile-ws
-> device_runtime 解码 NV21/JPEG 帧
-> VisionDetector 检测人物、人脸、手部
-> FrameProcessor 生成可靠检测结果和 overlay 数据
-> TrackingController 计算 pan/tilt 控制量
-> GimbalController 控制 TTL 总线舵机
-> 设备状态接口返回检测、云台、手势、AI 锁定状态
-> 手机端绘制模板框、骨架、目标点和 AI 推荐框
```

### 5.4 模板构图和自动跟随

```text
用户选择模板
-> 手机端或后端生成 template_data
-> template_data 包含 bbox_norm、head_bbox_norm、pose_points_image、pose_points_bbox、肩部/面部锚点
-> 手机端绘制模板 overlay
-> 手机把模板数据下发给 device_runtime
-> 设备端根据实时检测点和模板目标点计算偏移
-> 云台微调，使人物逐步进入模板推荐位置
```

模板构图不是大模型直接判断，而是工程化结构数据：

- 模板图先提取人体关键点、人物框和头肩锚点。
- 拍摄时实时检测人物位置，与模板目标位置比较。
- 控制器把偏移转换成云台 pan/tilt 动作。
- 大模型主要负责照片评分、背景分析、多角度候选选优和推荐框输出。

### 5.5 AI 自动找角度

```text
用户点击 AI 自动找角度
-> 手机进入倒计时
-> 手机按扫描配置控制云台转到多个候选角度
-> 每个角度等待稳定后，手机本地相机抓取当前帧
-> 手机把候选图和 candidate_index / pan_offset / tilt_offset 上传到 /api/mobile/ai/analyze-scan
-> 后端把所有候选图放进同一个视觉模型请求
-> AI 返回 best_candidate_index、score、summary、recommended_pan_delta、recommended_tilt_delta
-> 后端写入 ai_tasks
-> 手机找到最佳候选对应的角度
-> 手机调用设备控制接口，让云台转回最佳角度
```

### 5.6 AI 背景锁定

```text
用户点击 AI 背景锁定
-> 手机扫描多个候选背景角度
-> 后端让 AI 比较候选背景
-> AI 返回 best_candidate_index 和 target_box_norm
-> 手机控制云台回到最佳背景角度
-> 手机把 target_box_norm 绘制为推荐站位框
-> 设备端可应用锁机位，使后续跟随以推荐框为目标
```

### 5.7 连拍选优

```text
用户从历史照片中选择 2 到 9 张
-> 手机调用 /api/mobile/ai/batch-pick
-> 后端读取这些 capture 记录
-> AiProviderService 把每张图和 capture_id 一起发给模型
-> AI 返回 best_capture_id、summary、score
-> 后端校验 best_capture_id 必须来自本次请求
-> 后端标记最佳照片 is_ai_selected
-> 手机端显示 AI 选出的最佳照片和理由
```

### 5.8 管理后台配置 AI Provider

```text
管理员登录后台
-> 打开 AI Provider 配置页
-> 填写 vendor_name、provider_format、api_base_url、api_key、model_name、extra_config
-> 设置默认 Provider
-> 手机触发 AI 任务时，后端读取当前默认或套餐指定 Provider
-> 统一调用模型并记录任务
```

## 7. AI 调用设计

### 7.1 为什么 AI 放在后端

生产主链路不让手机或树莓派直接保存 AI Key，原因是：

- 防止 Provider API Key 泄露到客户端安装包或设备环境。
- 后台可以统一切换 Provider、模型名、base URL 和 API Key。
- 后端可以记录 `request_payload`、`response_payload`、失败原因和耗时信息，便于排查。
- 后端可以根据用户套餐控制 AI 能力。
- 手机端和设备端只需要关心任务结果，不需要处理不同模型厂商的兼容差异。

### 7.2 AI 图片打包

手机到后端：

```text
普通照片分析：
手机拍照
-> 保存到手机相册
-> 上传后端 /api/mobile/captures/file
-> 创建 capture 记录
-> 调用 /api/mobile/ai/analyze-photo 或 /api/mobile/ai/analyze-background

多角度扫描：
手机控制云台逐个转到候选角度
-> 每个角度等待稳定
-> 手机本地相机抓取当前画面
-> 存到临时文件
-> multipart 上传到 /api/mobile/ai/analyze-scan
```

`analyze-scan` 的 multipart 字段：

| 字段 | 内容 |
| --- | --- |
| `files` | 1 到 12 张候选图。 |
| `task_type` | `auto_angle` 或 `analyze_background`。 |
| `candidates_json` | 每张图对应的 `candidate_index`、`pan_offset`、`tilt_offset`。 |
| `metadata_json` | 入口、设备地址、会话、模板、扫描参数等上下文。 |
| `device_id` | 可选设备 ID。 |

后端到模型的 OpenAI-compatible 图片格式：

```json
{
  "type": "image_url",
  "image_url": {
    "url": "data:image/jpeg;base64,<base64>",
    "detail": "low"
  }
}
```

LongCat 视觉格式：

```json
{
  "type": "input_image",
  "input_image": {
    "type": "base64",
    "data": "<base64>",
    "_mime_type": "image/jpeg"
  }
}
```

图片压缩策略：

- 后端用 OpenCV 读取图片。
- 如果最长边超过 720，等比例缩放到最长边 720。
- 非 PNG 优先压缩为 JPEG，质量约 70。
- PNG 保留 PNG，但使用压缩等级处理。
- 再进行 base64 编码，放进模型请求。

模型请求大体结构：

```json
{
  "model": "<管理后台配置的模型名>",
  "messages": [
    {"role": "system", "content": "<系统提示词>"},
    {
      "role": "user",
      "content": [
        {"type": "text", "text": "<用户提示词>"},
        {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,...", "detail": "low"}}
      ]
    }
  ],
  "max_tokens": 800,
  "temperature": 0.2,
  "stream": false
}
```

### 7.3 AI 返回解析

后端处理模型输出的步骤：

```text
读取 choices[0].message.content
-> 去掉 ```json 这类 markdown fence
-> 尝试 json.loads
-> 如果模型夹杂解释文字，则用正则抽取第一个 JSON 对象
-> 归一化 task_type
-> 归一化 score 到 0-100
-> 限制 recommended_pan_delta
-> 限制 recommended_tilt_delta
-> 归一化 target_box_norm
-> 写入 ai_tasks
```

字段归一化规则：

- `score` 如果是 0 到 1，会乘以 100；如果是 1 到 10，会乘以 10；最终限制在 0 到 100。
- `recommended_pan_delta` 限制在约 -20 到 20。
- `recommended_tilt_delta` 限制在约 -15 到 15。
- `target_box_norm` 限制为 0 到 1 的归一化框，并保证宽高有合理下限。
- 多角度扫描的 `best_candidate_index` 必须来自候选列表。
- 连拍选优的 `best_capture_id` 必须来自本次请求的 `capture_ids`。

AI 任务成功时写入：

```text
status = succeeded
response_payload = 模型结构化结果
result_summary = summary
result_score = score
recommended_pan_delta
recommended_tilt_delta
target_box_norm
finished_at
```

AI 任务失败时也会落库：

```text
status = failed
response_payload = {"provider_metadata": ...}
error_message = 失败原因
finished_at
```

## 8. AI 智能体和提示词

项目里不是多个独立部署的 Agent 服务，而是按任务拆成多个 AI 角色。所有角色都通过后端或设备侧兼容接口调用视觉模型。

| 智能体 | 对应任务 | 核心作用 |
| --- | --- | --- |
| 照片构图分析 Agent | `analyze_photo` | 分析单张照片构图，返回评分、摘要、云台微调和推荐框。 |
| 背景分析 Agent | `analyze_background` | 分析背景和站位，返回更适合锁定的相机位置和推荐站位框。 |
| 自动找角度 Agent | `auto_angle` | 比较多角度候选帧，选择最佳候选角度。 |
| 背景锁定扫描 Agent | `analyze_background` + 多候选 | 在多角度候选中选择背景更干净的角度，并返回人物站位框。 |
| 连拍选优 Agent | `batch_pick` | 从多张连拍照片中选出最佳照片。 |
| 设备侧拍照助手 | 设备侧兼容接口 | 用于本地调试和兼容实验，不是生产主链路。 |

### 8.1 通用 JSON 字段

```json
{
  "task_type": "analyze_photo",
  "recommended_pan_delta": 2,
  "recommended_tilt_delta": -1,
  "target_box_norm": {
    "x": 0.31,
    "y": 0.14,
    "w": 0.36,
    "h": 0.70,
    "label": "recommended_person_position"
  },
  "summary": "人物略偏左，建议相机向右微调，背景整体较干净。",
  "score": 88
}
```

字段含义：

- `task_type`：AI 任务类型，例如 `analyze_photo`、`analyze_background`、`auto_angle`、`batch_pick`。
- `recommended_pan_delta`：推荐水平云台微调角度。
- `recommended_tilt_delta`：推荐俯仰云台微调角度。
- `target_box_norm`：推荐人物站位框，使用 0 到 1 的归一化坐标。
- `summary`：给用户看的中文解释。
- `score`：AI 评分，范围 0 到 100。
- `best_candidate_index`：多角度扫描时 AI 选中的最佳候选编号。
- `best_capture_id`：连拍选优时 AI 选中的最佳照片 ID。

## 9. 关键实现细节

### 9.1 手机主预览为什么不用树莓派画面

手机作为主预览有三个优势：

- 画质更稳定，最终拍照和录像来自同一个摄像头源。
- 避免树莓派回传画面带来的延迟、方向、压缩和网络问题。
- 手机端 overlay 可以直接贴合本地预览坐标系，减少坐标转换误差。

树莓派或本机设备运行时仍保留 `preview.jpg`、`preview-ws` 和 WebRTC 兼容链路，主要用于调试和扩展。

### 9.2 归一化坐标

项目里大量使用 0 到 1 的归一化坐标：

- `bbox_norm`：人物框。
- `head_bbox_norm`：头部框。
- `pose_points_image`：相对整张图的人体关键点。
- `pose_points_bbox`：相对人物框的人体关键点。
- `target_box_norm`：AI 推荐人物站位框。

好处是同一份结构可以跨手机预览、后端图片、设备检测帧和不同分辨率画布复用。

### 9.3 云台控制

云台控制分三层：

- `TrackingController`：负责根据目标点和期望点计算 pan/tilt 增量，包含死区、增益、刹车区和步进限制。
- `GimbalController`：负责角度限幅、平滑移动、live motion、feedback 和回中。
- `ServoDriver`：负责真实硬件或 mock 驱动。真实硬件通过 TTL 总线协议写入舵机角度。

### 9.4 AI 锁机位

AI 背景锁定返回 `target_box_norm` 后，手机端会把它显示为推荐站位框；设备端也可以应用这个框，使后续跟随目标不再是简单画面中心，而是 AI 推荐的人物位置。

### 9.5 失败降级

AI Provider 不可用时，后端不会让前端直接崩溃，而是创建失败状态的 `ai_tasks`：

- `status = failed`
- `error_message = 失败原因`
- `response_payload = provider_metadata`

手机端和后台都可以看到失败原因，例如 Provider 未启用、缺少 API Key、模型名为空、模型返回非 JSON、HTTP 错误等。

## 12. 项目讲解重点

面试或答辩时可以按这个顺序讲：

```text
项目背景
-> 自助拍摄痛点
-> 四端协同架构
-> 手机主预览 + 设备低延迟控制
-> 模板构图和归一化视觉数据
-> 后端 AI Provider 统一调用
-> AI 自动找角度 / 背景锁定 / 连拍选优
-> PostgreSQL JSONB 和 ai_tasks 可追踪落库
-> 后台管理和失败排查
```

一句话版本：

```text
云影随行是一个基于 Flutter、FastAPI、OpenCV/MediaPipe、PostgreSQL 和 OpenAI-compatible 多模态视觉模型的智能拍摄系统。系统以手机 App 作为主预览和最终媒体入口，树莓派/本机设备运行时负责边缘视觉检测与双轴 TTL 舵机云台控制，后端统一管理用户、模板、拍摄记录、AI 任务和 Provider 配置，支持模板构图、自动跟随、手势抓拍、AI 多角度找机位、背景锁定和连拍选优。
```

如果被问“AI 到底怎么接的”：

```text
生产主链路没有把大模型 Key 放在手机或树莓派上，而是集中放在后端 Provider 配置里。手机只负责上传照片或多角度候选帧，后端读取 Provider 配置后构造 OpenAI-compatible vision request。请求里包含 system prompt、user prompt 和图片内容；图片会被压缩到最长边约 720，再转成 base64 data URL。我们要求模型只返回 JSON，并约束字段包括 score、summary、recommended_pan_delta、recommended_tilt_delta、target_box_norm、best_candidate_index。后端解析 JSON 后会做分数归一化、角度限幅、推荐框归一化，最后写入 ai_tasks，手机端拿到结果后展示评分、推荐框或控制云台回到最佳角度。
```

如果被问“为什么不让树莓派直接做 AI”：

```text
树莓派更适合做低时延控制和轻量视觉检测，例如 MediaPipe 关键点、目标跟随和串口舵机控制。生产 AI Key 和模型调用放在后端更安全，也方便通过后台切换 Provider、记录 AI 任务、做套餐能力控制和失败降级。这样手机端和设备端都不需要保存生产 Key。
```

如果被问“模板构图是不是大模型做的”：

```text
模板构图主链路不是大模型直接判断，而是工程化的结构数据。模板图先通过 ML Kit 或 MediaPipe 提取人体关键点，生成 bbox、head box、pose points、肩部/面部锚点等归一化数据。拍摄时手机端绘制模板 overlay，设备端根据实时目标点和模板目标点的偏差控制云台微调。大模型主要负责照片评分、背景分析、多角度候选选优和推荐框输出。
```
