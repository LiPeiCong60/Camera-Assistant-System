## 0. 全局总状态图

这张总图不追求字段级细节，而是先把系统最重要的状态域拆开。

```mermaid
stateDiagram-v2
  [*] --> 系统入口

  系统入口 --> 手机独立拍摄域: 进入手机拍摄
  系统入口 --> 设备联动域: 进入设备联动
  系统入口 --> 历史与缓存域: 打开历史/模板

  state 手机独立拍摄域 {
    [*] --> 相机准备中
    相机准备中 --> 可拍摄
    可拍摄 --> 拍照中
    拍照中 --> 写历史中
    写历史中 --> 可拍摄
    写历史中 --> 写历史失败
    写历史失败 --> 可拍摄
    可拍摄 --> AI分析中
    AI分析中 --> AI结果可见
    AI分析中 --> AI失败
  }

  state 设备联动域 {
    [*] --> 会话未打开
    会话未打开 --> 会话已打开
    会话已打开 --> 推流未启动
    推流未启动 --> 推流中
    推流中 --> 预览回传中
    预览回传中 --> 设备功能运行中
    设备功能运行中 --> 推流中
    会话已打开 --> 会话关闭中
    会话关闭中 --> 会话未打开
  }

  state 历史与缓存域 {
    [*] --> 在线加载
    在线加载 --> 最新数据可见
    在线加载 --> 本地缓存回退
    本地缓存回退 --> 缓存数据可见
    本地缓存回退 --> 加载失败
  }
```

### 图意说明

这张图表达三个层次：

1. 手机独立拍摄域：围绕相机、拍照、写历史、AI 分析展开。
2. 设备联动域：围绕会话、推流、预览、云台和设备侧功能展开。
3. 历史与缓存域：围绕在线拉取与本地缓存回退展开。

## 1. 手机拍摄页状态图

这张图对应 `CameraCapturePage` 的核心用户态，不展开内部所有布尔字段，只保留对行为最重要的状态。

```mermaid
stateDiagram-v2
  [*] --> 准备中

  准备中 --> 就绪: 相机初始化成功
  准备中 --> 初始化失败: 相机异常
  初始化失败 --> 准备中: 用户重试

  就绪 --> 拍照中: 用户点击拍照
  拍照中 --> 写历史中: takePicture 成功
  拍照中 --> 就绪: 拍照失败

  写历史中 --> 就绪: 写 capture 成功
  写历史中 --> 写历史失败: 上传或入库失败
  写历史失败 --> 就绪: 用户继续操作

  就绪 --> AI分析中: 用户点击 AI 分析
  AI分析中 --> AI结果可见: AI 成功
  AI分析中 --> AI失败: AI 失败
  AI失败 --> 就绪: 用户继续拍摄或重试
  AI结果可见 --> 就绪: 用户继续拍摄
```

### 对应真实实现

- `准备中` 对应 `_isPreparing=true`
- `拍照中` 对应 `_isCapturing=true`
- `写历史中` 对应 `_isRecordingCapture=true`
- `AI分析中` 对应 `_isSubmitting=true`
- `写历史失败` 对应拍照成功但 `_uploadSingleCaptureRecord()` 失败

## 3. 后端 AI 任务状态图

这张图对应后端 `ai_tasks` 的真实状态演化。

```mermaid
stateDiagram-v2
  [*] --> 未创建
  未创建 --> 校验中: 用户请求 analyze-photo / background / batch-pick

  校验中 --> failed: session/capture/provider 校验失败
  校验中 --> pending: 校验通过并创建 ai_task

  pending --> 调用Provider中: 调用 AI Provider
  调用Provider中 --> succeeded: 返回有效分析结果
  调用Provider中 --> failed: Provider 调用异常或配置不可用

  succeeded --> [*]
  failed --> [*]
```

### 说明

这里的 `failed` 既可能来自：

- session / capture 不存在
- provider 未配置
- provider 配置不完整
- provider 调用失败

而 `succeeded` 对应数据库中任务已经写入结果摘要、分数和响应载荷。

## 4. 设备会话生命周期状态图

这张图对应 `device_runtime` 中 `SessionManager` 持有的单会话模型。

```mermaid
stateDiagram-v2

  无会话 --> 打开中: POST /api/device/session/open
  打开中 --> 会话已打开: 初始化 RuntimeState / Detector / Capture / Overlay 成功
  打开中 --> 无会话: 初始化失败
```

- 当前实现是“单会话模型”

## 7. 手势抓拍状态机

这张图直接对应 `GestureCaptureState` 的 `_phase` 和关键转移。

```mermaid
stateDiagram-v2
  [*] --> idle

  idle --> open: open 手势稳定达到阈值
  open --> idle: open 超时 / ready_for_pose_capture=false / reset
  open --> capture触发: fist 手势稳定达到阈值
  idle --> force_capture触发: ok 手势稳定达到阈值且 force_ok_enabled=true

  capture触发 --> cooldown
  force_capture触发 --> cooldown
  cooldown --> idle: cooldown 时间结束
```

### 真实逻辑补充

- `idle -> open`
  需要 open 手势持续稳定若干帧
- `open -> capture触发`
  需要 fist 手势持续稳定若干帧
- `force_capture触发`
  是独立通道，不依赖 open -> fist
- `ready_for_pose_capture=false`
  会直接把 `open` 相关状态清回 `idle`

### 总结

这份状态图文档可以压缩成三句话：

1. 当前项目最成熟的状态机在设备联动侧，尤其是会话、推流、模式切换、手势抓拍和设备端 AI。
2. 手机侧业务状态机比较清晰，但更多是“页面提交状态 + 缓存回退状态”，不是复杂实时状态机。
3. 离线补传、设备抓拍自动同步历史这类“跨系统补偿状态机”目前还没有真正建立起来。
